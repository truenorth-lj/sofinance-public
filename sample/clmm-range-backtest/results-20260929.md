## Correction Conclusion

The previous "10–12 ticks optimal" and "30 days approximately $13.65 per $1,000" are **retracted**. The old candidate generator missed odd tick widths and treated OHLCV high/low price scenarios as true fee bounds. After correction, **even using the exact same 30-day historical data, changing the entry price makes the optimal width shift from 11 ticks to 4 ticks**. All figures below are exploratory **historical income proxy values**, not actual fee backtests or guaranteed returns. Principal gains/losses, risk, rebalancing, position opening costs, and other rewards are not included, consistent with this exercise's focus on comparing trading fee income only.

## Algorithm Verification and Unverifiable Parts

1. `tick_price = 1.0001^tick × 10^(decimals_A − decimals_B)`, price direction is SPCXx/SPCX. The position formula converting fixed $1,000 to CLMM `L` has been verified against an actual snapshot using Raydium SDK's `TickUtil` and `LiquidityMathUtil`, with differences only in token raw-unit rounding.
2. Corrected candidate generator to enumerate all legal lower and upper bound ticks. Old version only searched even widths and cannot be used to claim optimality.
3. Income proxy value is `Σ[USD volume where bar closing price is in range] × L_ours / (L_pool_snapshot + L_ours) × 0.000084`. Each bar's volume does not all occur at the closing price; historical pool active liquidity is not equal to current snapshot; individual swaps may also cross multiple ticks. Therefore it cannot calculate true LP fees.
4. "Entire bar high/low within range" and "bar high/low touches range" are just two **volume classification scenarios**, not proven actual fee lower/upper bounds. The old report used this to assert 2 ticks must lose to 10 ticks, which is an invalid inference.
5. To precisely answer which segment historically earned the most fees requires individual swap directions and volume at each step, active liquidity and fee distribution at each tick at that time, then replay with the same $1,000 hypothetical position. This example lacks such data, so only provides exploratory ranking.
